### The one real bug, and the two-layer trap behind it

`GET /api/education-records` was **400 on live for every role**, and predated the merge (master has the
same `orderBy` and the same missing column). It was masked twice over:

1. `education_records` was provisioned before `createdAt`/`updatedAt` were in its `CREATE TABLE` body.

### `isSnapshot` — a page-killing crash, found by accident

Chasing a different problem, a synthetic Houseparent session crashed `/violations` with
`Cannot read properties of undefined (reading 'some')`. Root cause: `isSnapshot()` returned true for
**any object carrying a `fullAccess` key**, and `AuthContext` stores `fullAccess` on the session user
next to a null `access`. So the user object was mistaken for a resolved snapshot and the next read,
`snapshot.modules.some(...)`, threw. Reachable for any session restored from localStorage with no
`access` field — every role that is not a full-access role. A real snapshot always carries `modules`,
so the guard now requires `Array.isArray(modules)`.

**The near-miss matters more than the bug**: my first fixture set `access: null` while keeping
`fullAccess: false`, and I nearly wrote it off as a fixture artifact. It *was* unrealistic for a
session created by the current login (which always ships `access`) — but only because the login
payload happens to supply it. Building the fixture from the server's own `buildAccessSnapshot()` +
`listAccessibleMenus()` removed the guesswork, and the `access`-less case was then kept as a real
regression case. **Derive fixtures from the server's own code; do not hand-write a session shape.**
