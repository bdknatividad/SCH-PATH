## CORRECTION: the deploy was never stuck

I concluded from outside that production had frozen at 18:00. **That was wrong.**
With the Railway token the deployment list was readable directly:

```
09-24 18:54  SUCCESS   commitHash 9883316c959224fd40c2afa9b12a50e7d2065021
```

Every earlier entry was `REMOVED` (superseded), which is what made the list look
like a stall. The build had been working the whole time. The lesson: "no
behaviour change after a push" is not evidence that the deploy failed — it is
equally consistent with the code running and not doing what I assumed.

## The actual root cause: one duplicate key skipped the whole seed

From the runtime log of deployment `a01294bb`:

```
[10:54:22] [info]  Migration: empty nurse, educator, and houseparent access rows repaired from the role definition.
[10:54:22] [error] Seeding failed: Duplicate entry 'UHP01' for key 'users.PRIMARY'
[10:54:22] [info]  SCH-PATH Backend Server
```

`seedDatabase()` looked a user up **by username** and inserted **by id**. An
operator had renamed `HP 1` → `HP1` in Account Management, which freed the
username while the row kept the id `UHP01`. The lookup missed, the INSERT
collided, and because every step shared ONE try/catch the function unwound above
`reconcileSeededAccessGrants()`. The repair shipped, deployed, and ran on every
boot without ever executing — as did `seedResidentAssignments()` and the
violation-guide sync.

Fixed in `5b68857`: `runSeedStep` isolates each step; `seedDefaultUsers` treats
the id as the account's identity and reports the rename instead of throwing;
the reconciliation runs **first** so nothing downstream can skip it.

## Second bug, found in the same log

```
Incorrect date value: '' for column 'followUpDate' at row 1
  at insert (src/controllers/healthController.js:273)
```

`toMysqlDate` / `toMysqlDateTime` had `if (!trimmed) return trimmed`, so an empty
string passed through — and `''` is exactly what a browser submits for an
untouched `<input type="date">`. MySQL rejects it for DATE and DATETIME alike, so
this broke **every optional date field**, not just `followUpDate`. Empty now maps
to NULL. A non-empty unparseable value still passes through on purpose.

Note the test that had to change: `assert.equal(toMysqlDateTime(''), '')` was
asserting the bug, with a comment defending it. Distinguishing `''` (not set)
from `'not a date'` (a real typo) is the whole point.

## Environment trap: `EBUSY` on child processes

6 tests fail in this sandbox and **fail identically at HEAD**, so they are not
regressions:

```
spawnSync C:\...\22.22.2-3\node.exe EBUSY
```

The sandbox refuses to spawn the managed node binary as a child process. The 5
`jwt-secret` tests and the dialog-guard test all do that. Prove it by stashing
your changes and running the suite clean before blaming yourself — I nearly did.
