## The actual root cause: one duplicate key skipped the whole seed

From the runtime log of deployment `a01294bb`:

```
[10:54:22] [info]  Migration: empty nurse, educator, and houseparent access rows repaired from the role definition.
[10:54:22] [error] Seeding failed: Duplicate entry 'UHP01' for key 'users.PRIMARY'
[10:54:22] [info]  SCH-PATH Backend Server
```

`seedDatabase()` looked a user up **by username** and inserted **by id**. An
operator had renamed `HP 1` → `HP1` in Account Management, which freed the
username while the row kept the id `UHP01`. The lookup missed, the INSERT
collided, and because every step shared ONE try/catch the function unwound above
`reconcileSeededAccessGrants()`. The repair shipped, deployed, and ran on every
boot without ever executing — as did `seedResidentAssignments()` and the
violation-guide sync.

Fixed in `5b68857`: `runSeedStep` isolates each step; `seedDefaultUsers` treats
the id as the account's identity and reports the rename instead of throwing;
the reconciliation runs **first** so nothing downstream can skip it.

## Second bug, found in the same log

```
Incorrect date value: '' for column 'followUpDate' at row 1
  at insert (src/controllers/healthController.js:273)
```

`toMysqlDate` / `toMysqlDateTime` had `if (!trimmed) return trimmed`, so an empty
string passed through — and `''` is exactly what a browser submits for an
untouched `<input type="date">`. MySQL rejects it for DATE and DATETIME alike, so
this broke **every optional date field**, not just `followUpDate`. Empty now maps
to NULL. A non-empty unparseable value still passes through on purpose.

Note the test that had to change: `assert.equal(toMysqlDateTime(''), '')` was
asserting the bug, with a comment defending it. Distinguishing `''` (not set)
from `'not a date'` (a real typo) is the whole point.

# Session 2 — the QPR "Unable to display the report form." report

Badek tried to open a QPR as `centerhead` and got the red sentence in the
editor. Screenshot timestamp `2026-09-25T04:50Z` (12:50 GMT+8), URL
`sch-path.vercel.app/reports`, browser **Chrome** (the browser is identifiable
from the other clipboard shots in `~/.workbuddy-ai/clipboard-images/`).

## What the error actually was

`QuarterlyProgressReport.tsx` has **two** different sentences and they mean
different things:

- `Unable to load the report form.` — the `fetch` failed (`!response.ok`).
- `Unable to display the report form.` — the fetch **succeeded** and pdf.js
  could not render the body. This is the `error` prop of `<PdfDocument>`.

The screenshot showed the second, so a 200 body had been handed to pdf.js.

## Ruled out, with evidence

- **The PDF is fine.** Fetched every live template (`QPR001/002/003`): all
  `200 application/pdf`, `%PDF-` magic, and all **parse to 2 pages** in Node
  with the *same* `pdfjs-dist/legacy/build/pdf.mjs` the browser loads.
- **Not a version mismatch.** Deployed `pdf.worker.mjs` reports `5.4.296`; the
  pdfjs inside the deployed `TextLayer-*.js` chunk reports `5.4.296`.
- **Not the API base.** The deployed entry chunk contains
  `https://sch-path-production.up.railway.app/api`, and the deployed `Reports`
  chunk builds the template URL through the minified `apiUrl` (`Ie(...)`), not a
  literal. So `VITE_API_URL` is set on Vercel and the fix from `c5d95f1` is live.
- **Not CSP.** `vercel.json` sets only `frame-ancestors 'self'`; `index.html`
  has no `<meta http-equiv>`. Nothing blocks workers.
- **Not StrictMode.** It is not used.
- **Not caching of the entry HTML.** `index.html` is
  `public, max-age=0, must-revalidate`; the hashed `/assets/*` are immutable,
  which is correct for hashed names.
- **Not the browser.** Drove the **live** site with Playwright in headless
  **Edge** *and* **Firefox**: the QPR renders 2 canvases (`900x1272`), zero
  console errors, including the create-a-QPR dialog flow. Then swept all 12
  sidebar modules for `centerhead`: **0 findings** (no console errors, no
  failed requests, no 4xx/5xx).
- **The backend is not serving the SPA**, so the Railway origin is not an
  alternative frontend — `GET /` there is a JSON 404.

So the live path is healthy. The one code path that *can* produce that exact
sentence is the pre-`c5d95f1` shape: a raw `fetch` whose only check is
`res.ok`, fed a 200 that is actually the SPA's `index.html`. Note the baseline
`api.ts` hardcoded `'/api'` in production, so **any** tab loaded before
2026-09-23 12:34 was broken everywhere, not just here — the most likely reading
is a long-lived tab, but that is inference, not proof. Do not claim more.

## What was fixed anyway (commit `a7ffc0a`)

The sentence was real even if the trigger was environmental: **the class of bug
was still open in every binary endpoint.** All of them checked `res.ok` and then
trusted the body.

- `api.ts` → new `fetchBinary(path, init)`. Joins the base through `apiUrl`,
  checks the status, then the **shape**: an HTML body throws
  *"The file request did not reach the API — the server answered with a web page
  instead of the file."* It also reads the RFC 6266 filename, which three call
  sites were parsing by hand.
- Callers switched to it: `utils/documentFile.ts`, `DocumentUpload.tsx` (view,
  print, bulk ZIP), `PhaseProgress.tsx`, `AnecdotalReports.tsx`,
  `QuarterlyProgressReport.tsx` (both `/pdf` and `/template`).
  **`.blob()` now exists in exactly one place** (`fetchBinary`), which is what
  the new test pins.
- QPR: re-fetch the form **once per report** on a viewer failure (the usual
  cause is the object URL being revoked under the worker), and on a second
  failure report the *reason* instead of the fixed sentence.
- `quarterlyProgressReportController.js` → `sendPdf()` checks the `%PDF-`
  signature before writing, so a generator fault is a **500 where it happened**
  instead of a 200 the client can only describe as a broken viewer. Exported for
  tests.
- `vercel.json`: `/pdf.worker.mjs` was `immutable, max-age=31536000` **at an
  unhashed URL**. That is a live landmine — the next pdfjs upgrade would give
  every returning visitor a worker that does not match the library, i.e. this
  exact symptom for everyone who had visited before. Now
  `max-age=0, must-revalidate`; the file has an ETag (`cb3ffcb8…`) so the cost
  is a 304. **JSON cannot carry a comment, which is why it is written here.**

# Session 3 — the worker URL was the poison, not the header

## What the user actually reported

> Unable to display the report form (Setting up fake worker failed: "Failed to
> fetch dynamically imported module:
> https://sch-path.vercel.app/pdf.worker.mjs".). when i create a QPR that shows

The parenthetical is the real error — and it is *my* improved reporting from
`c368472` that surfaced it. Worth remembering: the error-message work is what
produced the diagnosis, not a side quest.

## Root cause, proven from git history

`vercel.json` at `c5d95f1` (Sep 23 **12:34**) declared `Content-Type` on
`/pdf.worker.mjs` **twice**: once as `text/javascript`, then a later, broader
rule sending `(pdf.worker.mjs|tri-form.pdf)` as `application/octet-stream`. Vercel
merges every matching header rule and **the last match wins**, so the worker went
out as octet-stream, with `X-Content-Type-Options: nosniff` on top. A browser
will not execute that as a module.

Corrected 2h23m later in `2437e39` (Sep 23 **14:57**) — *but* the worker was also
under `Cache-Control: public, max-age=31536000, immutable`. **`immutable` means
the browser does not revalidate for the freshness lifetime**, so every browser
that loaded the app during those 2h23m kept the octet-stream copy for a year.
A header fix cannot reach a cache entry like that.

That is the whole shape of "works for me, broken for you": my test browsers were
fresh profiles, so they never held the poisoned entry.

## The fix — a new URL, because only a new URL is a new cache key

All 7 `GlobalWorkerOptions.workerSrc` assignments now build
`` `/pdf.worker.mjs?v=${pdfjs.version}` ``. Taking the version from `pdfjs` itself
means a library bump changes the key, so the worker can never drift out of step
with the API loading it. Files: `AnecdotalReport.tsx`, `AnecdotalReports.tsx`,
`ChildDetail.tsx`, `ChildRecords.tsx`, `IncidentReportModal.tsx`,
`QuarterlyProgressReport.tsx` (carries the explanatory comment the others point
at), `Tri.tsx`.

`vercel.json` (already in `a7ffc0a`) drops `immutable` for
`public, max-age=0, must-revalidate`. The file has an ETag, so revalidating is a
304.

## Verification — the test that actually settles it

A fresh-profile render proves nothing here, so `C:/tmp/qpr-poison-test.js` models
the poisoned cache directly: it intercepts the **bare** `/pdf.worker.mjs` and
answers it with octet-stream + nosniff + `immutable` (exactly the old broken
response), while the versioned URL passes through. Then it logs in and opens a
QPR.

Result in **both Edge and Firefox**:

```
requests to the BARE worker url (must be 0):   (none)
requests to the VERSIONED url:                 https://sch-path.vercel.app/pdf.worker.mjs?v=5.4.296
canvases rendered: 2
shows the failure message? false
console/page problems: 0
PASS
```

The app no longer requests the poisoned URL at all. The screenshot
(`C:/tmp/shot-qpr-poison.png`) shows the full form: header, IDENTIFYING
INFORMATION, the six-Developmental-Aspect table, footer.

Also confirmed on the live deploy:

- `index-Bx0uPNzb.js` → **`index-BfX7hND8.js`**.
- The QPR component is bundled into `Reports-BLTA7kf6.js`, which now reads
  `` nt.workerSrc=`/pdf.worker.mjs?v=${rt}` `` — versioned.
- Across all 57 referenced chunks: **6 versioned worker URLs, 0 bare literals**
  (`TextLayer-*.js` also mentions the string but is pdfjs's own code).
- Both the bare and the versioned URL now answer
  `Content-Type: text/javascript; charset=utf-8`,
  `Cache-Control: public, max-age=0, must-revalidate`, 1906302 bytes, ETag
  `cb3ffcb8477f65845f30287649257403`.
- Full module sweep (12 modules): **0 findings**. QPR renders 2 canvases.
- API: health ok; QPR template + pdf, `DOC011` PDF, `DOC010` PNG all real files
  with correct magic bytes.

`backend/tests/pdf-worker-cache-key.test.js` pins both halves — no bare
`/pdf.worker.mjs` may survive in `frontend/src`, and the header rule must not be
`immutable`, must revalidate, must stay `javascript`, and must stay out of the
SPA rewrite. Mutation-checked: reverting either half fails exactly the intended
test.

Full suite after the change: **1102 tests, 1096 pass, 6 fail** — the 6 known
`EBUSY` child-process failures, unchanged.

## The lesson worth keeping

`immutable` on an **unhashed** path is a one-way door. Hashed assets
(`/assets/index-BfX7hND8.js`) are safe to mark immutable because a change produces
a new filename. `/pdf.worker.mjs` is not hashed, so an immutable response is one
no future fix can reach — the only cure is to change the URL. Reach for
`must-revalidate` on any unhashed path, and when a URL is already poisoned, ship a
new URL rather than a corrected header.
