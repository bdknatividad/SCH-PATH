## What was fixed anyway (commit `a7ffc0a`)

The sentence was real even if the trigger was environmental: **the class of bug
was still open in every binary endpoint.** All of them checked `res.ok` and then
trusted the body.

- `api.ts` → new `fetchBinary(path, init)`. Joins the base through `apiUrl`,
  checks the status, then the **shape**: an HTML body throws

  instead of the file."* It also reads the RFC 6266 filename, which three call
  sites were parsing by hand.
- Callers switched to it: `utils/documentFile.ts`, `DocumentUpload.tsx` (view,

- QPR: re-fetch the form **once per report** on a viewer failure (the usual

- `vercel.json`: `/pdf.worker.mjs` was `immutable, max-age=31536000` **at an

# Session 3 — the worker URL was the poison, not the header

## What the user actually reported

> Unable to display the report form (Setting up fake worker failed: "Failed to
> fetch dynamically imported module:
> https://sch-path.vercel.app/pdf.worker.mjs".). when i create a QPR that shows

The parenthetical is the real error — and it is *my* improved reporting from
`c368472` that surfaced it. Worth remembering: the error-message work is what
produced the diagnosis, not a side quest.

## Root cause, proven from git history

`vercel.json` at `c5d95f1` (Sep 23 **12:34**) declared `Content-Type` on
`/pdf.worker.mjs` **twice**: once as `text/javascript`, then a later, broader
rule sending `(pdf.worker.mjs|tri-form.pdf)` as `application/octet-stream`. Vercel
merges every matching header rule and **the last match wins**, so the worker went
out as octet-stream, with `X-Content-Type-Options: nosniff` on top. A browser
will not execute that as a module.

Corrected 2h23m later in `2437e39` (Sep 23 **14:57**) — *but* the worker was also
under `Cache-Control: public, max-age=31536000, immutable`. **`immutable` means
the browser does not revalidate for the freshness lifetime**, so every browser
that loaded the app during those 2h23m kept the octet-stream copy for a year.
A header fix cannot reach a cache entry like that.

That is the whole shape of "works for me, broken for you": my test browsers were
fresh profiles, so they never held the poisoned entry.

## The fix — a new URL, because only a new URL is a new cache key

All 7 `GlobalWorkerOptions.workerSrc` assignments now build
`` `/pdf.worker.mjs?v=${pdfjs.version}` ``. Taking the version from `pdfjs` itself
means a library bump changes the key, so the worker can never drift out of step
with the API loading it. Files: `AnecdotalReport.tsx`, `AnecdotalReports.tsx`,
`ChildDetail.tsx`, `ChildRecords.tsx`, `IncidentReportModal.tsx`,
`QuarterlyProgressReport.tsx` (carries the explanatory comment the others point
at), `Tri.tsx`.

`vercel.json` (already in `a7ffc0a`) drops `immutable` for
`public, max-age=0, must-revalidate`. The file has an ETag, so revalidating is a
304.

## Verification — the test that actually settles it

A fresh-profile render proves nothing here, so `C:/tmp/qpr-poison-test.js` models
the poisoned cache directly: it intercepts the **bare** `/pdf.worker.mjs` and
answers it with octet-stream + nosniff + `immutable` (exactly the old broken
response), while the versioned URL passes through. Then it logs in and opens a
QPR.

Result in **both Edge and Firefox**:

```
requests to the BARE worker url (must be 0):   (none)
requests to the VERSIONED url:                 https://sch-path.vercel.app/pdf.worker.mjs?v=5.4.296
canvases rendered: 2
shows the failure message? false
console/page problems: 0
PASS
```

The app no longer requests the poisoned URL at all. The screenshot
(`C:/tmp/shot-qpr-poison.png`) shows the full form: header, IDENTIFYING
INFORMATION, the six-Developmental-Aspect table, footer.

Also confirmed on the live deploy:

- `index-Bx0uPNzb.js` → **`index-BfX7hND8.js`**.
- The QPR component is bundled into `Reports-BLTA7kf6.js`, which now reads
  `` nt.workerSrc=`/pdf.worker.mjs?v=${rt}` `` — versioned.
- Across all 57 referenced chunks: **6 versioned worker URLs, 0 bare literals**
  (`TextLayer-*.js` also mentions the string but is pdfjs's own code).
- Both the bare and the versioned URL now answer
  `Content-Type: text/javascript; charset=utf-8`,
  `Cache-Control: public, max-age=0, must-revalidate`, 1906302 bytes, ETag
  `cb3ffcb8477f65845f30287649257403`.
- Full module sweep (12 modules): **0 findings**. QPR renders 2 canvases.
- API: health ok; QPR template + pdf, `DOC011` PDF, `DOC010` PNG all real files
  with correct magic bytes.

`backend/tests/pdf-worker-cache-key.test.js` pins both halves — no bare
`/pdf.worker.mjs` may survive in `frontend/src`, and the header rule must not be
`immutable`, must revalidate, must stay `javascript`, and must stay out of the
SPA rewrite. Mutation-checked: reverting either half fails exactly the intended
test.

Full suite after the change: **1102 tests, 1096 pass, 6 fail** — the 6 known
`EBUSY` child-process failures, unchanged.

## The lesson worth keeping

`immutable` on an **unhashed** path is a one-way door. Hashed assets
(`/assets/index-BfX7hND8.js`) are safe to mark immutable because a change produces
a new filename. `/pdf.worker.mjs` is not hashed, so an immutable response is one
no future fix can reach — the only cure is to change the URL. Reach for
`must-revalidate` on any unhashed path, and when a URL is already poisoned, ship a
new URL rather than a corrected header.

code           : ENOENT

document and no way to re-run the publish."* The TRI does the opposite, on purpose

but it makes a retry path mandatory. There wasn't one.

2. `tests/tri-docker-assets.test.js` pins the invariant: every frontend file the

   and only one has to survive into the image. Mutation-checked — removing the
   COPY line fails exactly the two intended tests.
3. `publishMissingTriDocuments()` — the retry path the non-fatal publish needs.

4. `finalize` returns `documentError`; `Tri.tsx` warns when the form was not filed

5. Boot logs the TRI template **and** layout — the Anecdotal Report already had

# Real-time notifications (the user's 4th request)

> "Fix din natin yung mga notifications dapat real time sila nalabas sa live
> deployment. for example sa hp nag gawa ng report tri or anecdotal mag nonotify
> dapat yung sa dapat mag approved like centerhead or socialworker."

## The mechanism was never the problem — the latency was

Probing live before changing anything: centerhead already saw 4 alerts,
socialworker 10 (9 unread), including `ALR036 "Anecdotal Report needs review"` and
TRI alerts. So notifications were being *written* correctly. The feed was
**pull-only** — `Notifications.tsx` polled `GET /api/alerts` every 30s plus on
window focus — so a submission took up to half a minute to appear, and only if the
reader came back to the tab.

## The fix

`backend/src/services/alertStream.js` (new) is an in-process SSE registry;
`GET /api/alerts/stream` holds the response open. `notificationService.notify()`
publishes **after** the row is written and before it returns the id.

Two decisions worth keeping:

- **The frame carries no data.** `event: alerts\ndata: {}` is a bare "re-read the
  feed". The client answers it with the same scoped `GET /api/alerts`, which is
  the single implementation of the visibility rule. Putting the alert body on the
  wire would create a second, weaker definition of who may see what — i.e. a leak.
  A signal delivered to a superset is a wasted refresh, never a disclosure.
- **Publish only after a real write.** A suppressed `ER_DUP_ENTRY` is not news;
  signalling it would make every page reopen — which re-fires the same business
  event — look like an incoming notification.

Client side: `streamAlerts()` in `api.ts` uses `fetch` + `ReadableStream`, **not

## Wall-clock columns, and a 500 found while verifying them

The response-boundary fix assumed every DATETIME on the wire holds UTC. True for
anything the server writes; **false for a column the user fills from a
`datetime-local` control**. That control has no zone, the value goes to MySQL as a
naive string, and `toMysqlDateTime` passes a naive string through — so
`incidentReports.incidentDateTime` and `intervention_tracker.scheduledAt` hold the
wall-clock the user typed. Reading them as UTC moved them eight hours, i.e. the
same defect the boundary fix removes, pointing the other way.
`InterventionTracker.tsx` renders `new Date(step.scheduledAt).toLocaleString()`,
so it was visible.

The earlier "the database is uniformly UTC" evidence was taken from `uploadedAt`
(a client `toISOString()`) against `createdAt` (`NOW()`) — both server-produced,
so it could not have detected a user-typed column. Two columns, one rule.

Fix: `WALL_CLOCK_DATETIME_COLUMNS` names them and `withIsoInstants` walks with the
property name, labelling them `+08:00` instead of `Z`. Labelling rather than
leaving bare keeps the "every datetime carries an offset" invariant and every
plain-text reader keeps working, because they look at the front of the string
(`slice(0, 16)`, `formatShortDate`'s `split('T')`). Storage untouched, no
migration.

Also fixed the other half — values the *browser* invents. `toISOString()` is UTC,
so `slice(0, 10)` is the UTC day (yesterday in Manila until 08:00, so an Anecdotal
Report opened in the first working hour was dated the day before) and
`slice(0, 16)` is the UTC wall-clock (Form 08 offered 06:40 AM on a form opened at
2:40 PM). `getCurrentPHDate()` existed; `getCurrentPHDateTime()` is new.

### The generalisation — a copy must be as wide as its source

Rather than widen the one column that happened to error, the whole flow was
audited against the **declared width of every column it copies**:

| column | copies | declared bound | was | now |
|---|---|---|---|---|
| `violations.type` | `guide.name` | `violation_guide.name VARCHAR(500)` | 100 | **500** |
| `assessments.triggeredBy` | framed guide name | 500 + 25-char frame = 525 | 100 | **600** |
| `assessments.title` | activities + ` — ` + resident | 111 + 3 + `children.name` 150 = 264 | 150 | **300** |
| `assessments.type` | activities joined | 111 | 100 | **255** |

`violations.type` was a **third live bug nobody had hit yet**: `create()` writes
`type: guide.name` straight through `buildInsertPayload`, and **10 of the 33
official guide names exceed 100 characters** (longest **189**), so logging any of
those violations failed at *creation* with the same masked error. Measured from
`OFFICIAL_VIOLATION_GUIDE`, not sampled.

Two things this ruled *out*, checked rather than assumed:

- `intervention_requirements.title VARCHAR(150)` receives
  `interventionOfficialText()` = `metadata.officialText`. The longest official
  intervention text is **118** (33 guides × 3 levels × ~4 entries = 237), so it
  fits. `parseGuideRequirement()` stores the canonical short type in
  `interventionType` ("Psychosocial Activity", 21 chars) and the narrative in
  `metadata.officialText`, so `intervention_tracker.interventionType VARCHAR(100)`
  is safe too — the 118-character strings never reach it.
- `violationController.js:812` is the **only** `INSERT INTO assessments` in
  `src/`, so the widths cover every writer.

### The fix

`ensureColumnLength(table, column, minLength, definition)` — reads
`CHARACTER_MAXIMUM_LENGTH` from `INFORMATION_SCHEMA.COLUMNS` first and only
`ALTER`s when the current width is short, so it is idempotent and cheap on every
later boot. It returns `false` if the column is absent, so a missing table cannot
take later statements down with it. Logs
`Migration: <table>.<column> widened to <def> (was <n>).` only **after** the ALTER
succeeds — which makes the boot line the proof of the repair.

Applied in `schema.sql` **and** the `server.js` `CREATE TABLE`s (both must agree),
plus the four `ensureColumnLength` calls in the boot migration. `schema.sql` alone
would have fixed nothing: nothing executes it.

### `tests/assessments-column-widths.test.js` (6 tests)

Every bound is derived from the **declaration of the source column**, read out of
`schema.sql`/`server.js` — not from a sample row, and not from a hand-copied
constant. `widthEverywhere()` also asserts the two files agree, so widening one
without the other fails. The rule it encodes: *a column that copies another
column must be at least as wide as the column it copies.* Widening
`violation_guide.name` without widening `violations.type` now fails in CI instead
of in production.

All five guards **mutation-verified** (`C:/tmp/mutate-widths.js`, driven from bash
— a node process cannot spawn the managed node binary). Each case narrows a column
in **both** files, so the mutation is a genuine regression rather than a
schema/server disagreement the test would catch for a different reason. Each
failed **exactly its intended test and nothing else**; `matched 1 occurrence(s)`
printed for every edit; restore is an unconditional `copyFileSync`.

Test-parser bug found and fixed on the way: `declaredWidth`'s column regex was
anchored at `^` with the `m` flag, but every column line is indented
(`  triggeredBy VARCHAR(255) NULL,`), so it returned `null` and
`null >= required` was `false` — three tests failed for a reason that had nothing
to do with the widths. Anchor on `^\s*`. **A parser that returns null silently
turns every bound assertion into a failure-or-pass for the wrong reason** — worth
checking whenever a width/contract test fails wholesale.

## The official-guide seeding churn (found in the `2a108ed` deploy log)

The boot log for `2a108ed` carried
`Seeding step failed (official violation guide): … fk_tracker_guide_intervention …`.
**`2a108ed` did not cause it** — its diff is `childController.readmit` plus a test,
neither of which can create a tracker row.

**Root cause, one line.** `parseGuideRequirement()` in `seedDatabase.js` stores
`officialText: ''` for a requirement resolving to `Psychosocial Activity`, but
`seedOfficialViolationGuide()` compared the stored rows against the **raw** source
text. Those can never be equal, so **52 of the 99 guide × offense-level sets were
deleted and re-created on every boot** — 154 fresh `guide_interventions` ids per
restart. Reproduced offline to the digit (99 sets / 47 match / 52 churn / 154 rows)
and confirmed live: **52 of 52** Psychosocial rows carry an empty `officialText`
(control: all 185 non-Psychosocial rows are populated), and ids reached **GI4857**
for 237 live rows — a span of 4,840 ≈ 31 boots × 154.

**Why it surfaced exactly then.** `VG019/1st` is the *only* set referenced by live
`intervention_tracker` rows that also churns (every other referenced set — VG031,
VG011, VG004, VG023, VG032 — is stable). The 08:02 boot minted `GI4752`–`GI4755`;
the user then verified VG019 violations against them; the 08:38 boot's DELETE hit
`ON DELETE RESTRICT` and **rolled the whole sync transaction back**. No data was
lost, but the sync was permanently aborted and would have failed on every boot.

**Fix:** compare the stored form
(`parsedRequirements.map(p => p.metadata.officialText)`), parse once and reuse the
parsed form in the INSERT loop, and add `ORDER BY createdAt ASC, id ASC` so a
same-second tie cannot flip an order-sensitive comparison. Pre-flighted against the

`tests/official-guide-seed-idempotence.test.js` — 5 guards: 2 behavioural through a
fake `pool.getConnection()`, 1 negative control (a genuinely stale set must still be
repaired), 1 production-signature pin (52 sets / 154 rows), 1 structural.
Mutation battery: `mutate1` (raw-text comparison restored) fails 2/4/5, `mutate2`
(tie-break dropped) fails 5, `mutate3` (parse-once link broken) fails 2/4.
Suite **1224 / 1218 pass / 6 fail** (the known `EBUSY` six).

**Lesson:** an idempotence check must compare against the value the code **stores**,
not the value it reads. When a transform sits between read and write, the check has
to go through the same transform — otherwise the "already correct" branch is
unreachable and the writer churns forever. It stays silent until something
references the churned rows, and then it looks like the referencing feature broke.

## Force-discharge → re-intake: `readmissionDatetime` written as ISO 8601

Reported while testing item 4: force-discharge a child, re-intake them, and the UI answers
`{"message":"Database error occurred"}`. The UI cannot say more — `errorHandler` maps every `ER_*`
code to that one sentence and drops `err.message` in production — so the Railway runtime log is the
only place the cause exists, and it named it in one call:

```
message: "Incorrect datetime value: '2026-09-25T09:24:06.144Z' for column 'readmissionDatetime' at row 1"
path: '/api/admissions', method: 'POST'
```

**Cause, and why it recurred.** `new Date().toISOString()` is ISO 8601; MySQL refuses the `T`, the
`Z` and the fractional seconds for a DATETIME column under the default strict `sql_mode`. The class
had already been fixed for *client-supplied* fields — `normalizeDatetimes` on request bodies,
`toMysqlDateTime` in `assignmentController` — and the two remaining sites were the
*server-generated* ones, which the middleware can never reach because it walks `req.body`:

- `admissionController.js` in the `POST /api/admissions` transaction (the path the user hit)
- `childController.js` `readmit` — the legacy `POST /children/:id/readmit` route

Both now bind `toMysqlDateTime(new Date())`. Chosen over wrapping the `toISOString()` call so the
call site contains **no** ISO string, which is what lets the class sweep prove it.

**Verified.** Deploy `47a5f19` → `f7cdbf4f` SUCCESS, clean boot. Live state confirms the failure was
clean: `CH001` is still `Discharged` with `readmissionDatetime = NULL`, i.e. the transaction rolled
back and left no half-written row. Also confirmed statically that no *other* bind in that transaction
is a datetime — the rest are DATE columns (`admissionDate`, `enteredAt`, `completedAt`) or plain
values, and the first-admission branch never sets `readmissionDatetime` at all, which is why only a
returning resident hit this.

**Guard.** `backend/tests/readmission-datetime-cutoff.test.js` — 5 tests: the helper's output shape,
a pin on each of the two sites, and a sweep over every `src/controllers/*.js` asserting no
`toISOString()` result is left unreduced. One allowlist entry, `reportController.js:generatedAt`
(a DSWD payload field; only `dswdReport.statistics` is persisted, and `generatedAt` sits beside it).
The sweep also asserts the allowlist is not stale, which doubles as proof the sweep reached the file
it names. Five mutations, all five fired: revert each site to ISO, swap the helper for `String(new

**The 401 probe is vacuous — check the authenticated status, not the anonymous one.**

expecting `401` to mean "the route exists" and `404` to mean it does not. It returned

before the router**, so every unknown path under `/api` answers 401 and the probe
proves nothing. The discriminator has to be authenticated: with a token, a bogus *path*
gives `404` while a bogus *line* gives `400 line must be one of centerhead, sectionchief`
from the handler's own map. General rule: **an auth middleware ahead of routing turns
404 into 401, so "it answered 401 not 404" is never evidence a route is mounted.**

## The label is not the value

## Schema — a NOT NULL column is a silent feature blocker

Both columns are `NULL` in the boot DDL **and** `schema.sql`, plus a guarded boot migration.
`CREATE TABLE IF NOT EXISTS` does nothing to an existing table, so the deployed database would keep
refusing without it. The migration reads `IS_NULLABLE` from `INFORMATION_SCHEMA.COLUMNS` **first** —
so it is a no-op where the column is already nullable and does not rebuild the table on every boot —
then `ALTER TABLE … MODIFY COLUMN`, all in `try/catch` with a `console.warn`, so a missing table or
privilege cannot stop the boot.

## Form — and normalizing at every boundary

- `isNotEnrolled(level)` is one predicate; the name is always required, the placement fields only
  inside `if (!isNotEnrolled(studentForm.educationLevel))`.
- Both labels drop their asterisk, with a "Not enrolled in school" hint.
- An empty school/date is sent as `null`: **an empty string is not NULL for a DATE column**, and MySQL
  refuses `''` under the default strict `sql_mode`.
- `normalizeStudent` runs on **every** path that puts a record into state — the cache load, the API
  load, and **all four** save responses (create, update, and the two file-upload `.then` handlers) — or
  the `null` that comes back reaches a controlled input. `mapRow` copies only declared columns, so the
  two columns had to be in `RESOURCES[].columns` as well.
- The wire type is honest (`EducationRecordWire` with `string | null`), which is what cleared the one
  new `tsc` error.

## API — a frontend-only rule is a suggestion

`requireEducationPlacement` in `middleware/validation.js`, on both the create and the edit route. A
school placement with no school or date is a **400 with the middleware's own message** — not a masked
500. A body that never mentions `educationLevel` (the file-upload path sends only `files`) is left
alone.
