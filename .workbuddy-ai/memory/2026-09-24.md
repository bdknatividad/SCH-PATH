## Phase 8 — Notifications. One defect found and fixed.

### FIXED: `POST /alerts` answered 500 for a bad request

`alertController.create` passed the body straight to `notificationService.notify()`,
which raises a **plain `Error`** for a missing title/message/addressee. A plain
Error is not an `ApiError` and has no `ER_` code, so `errorHandler` fell through
to its default: **500**, with the message masked to "Internal server error" in
production. The caller got a server fault with nothing to act on.

Measured against the deployed API before the fix:

    POST /alerts {}                    -> 500
    POST /alerts {title, message}      -> 500   (no addressee)
    POST /alerts {targetRole}          -> 500   (no title/message)

Fixed by validating in the controller (400s) before calling the service, plus a
new guard: an unrecognised `targetRole` is rejected instead of being stored
verbatim. An unknown role produces a row addressed to a role nobody holds —
readable by nobody — which is the same unreadable shape as the 14 legacy
addressee-less rows the service already documents as a bug.

Safe to change: the frontend has **no create-alert UI at all** and never sends
`targetRole` (only reads it), so `POST /alerts` is API-only. Nothing on screen
could break.

**Technique worth reusing — a behavioural controller test with no database.**
Validation runs *before* any I/O, so the controller can be driven directly with
fake `req`/`res` and a `next` that captures the error, and the assertion can be
on the real status code rather than on source text. This is stronger than the
repo's usual file-scanning style and is how the 500 was pinned. `config/database`
builds a pool at import but `createPool` does not connect, so requiring the
controller is safe.

**And the fix was verified by breaking it.** The validation was neutered in place
(three `if`s → `if (false)`, the two `throw` lines deleted), the suite re-run to
confirm the new test *failed* (39 pass / 1 fail — exactly the new test), then the
fix restored. A guard that cannot fail is decoration; this one was proven.
Restoring needed care: **`git checkout` would have been wrong** because the fix
was uncommitted, so HEAD did not contain it.

### FOUND, NOT FIXED: `DELETE /alerts/:id` destroys a shared alert for everyone

`/alerts` is mounted with `authenticate` only — no module guard. `remove()`
deletes the row itself (`DELETE FROM alerts WHERE id = ?`) plus its `alertReads`,
and the only check is `findVisible`, i.e. "can I see it". So **any authenticated
user who can see a role-addressed alert can delete it for every other
recipient** — 11 Houseparents share one alert and any one of them removes it from
all 11 feeds.

This contradicts the module's own central design principle. Read state was moved
to a per-user `alertReads` table precisely so one recipient's action could not
affect another's view; deletion is the one operation still global.

Reachable from the UI: `DataContext.tsx:1025` calls `deleteResource('alerts', id)`
and `Notifications.tsx` exposes `deleteAlert` to every role.

Probed non-destructively (non-existent id, so nothing could be deleted):

    DELETE /alerts/ALR_NONEXISTENT_PROBE  as nurse       -> 404  (reachable; no guard)
    DELETE /alerts/ALR_NONEXISTENT_PROBE  as centerhead  -> 404
    PUT    /alerts/ALR_NONEXISTENT_PROBE  as nurse       -> 404  (reachable)

A 404 rather than a 403 is the tell: the route is reachable and the only thing
that stopped it was visibility.

Needs a decision, not a patch. Options: (a) add an `alertDismissals` table and
make dismissal per-user, consistent with `alertReads` — correct, but a schema
change; (b) restrict DELETE to `targetUserId === me` or a manager role — small,
but it 404s the existing per-user "dismiss" button for role-addressed alerts.
Both change UX, so this is the user's call.

### FOUND, NOT FIXED: unbounded fetches in two read paths

`getByResident` calls `listFor(req.user)` with **no limit** — the whole alert
history — then filters by `residentId` in JS. `getUrgent` does the same and then
slices 10. Both are `LIMIT`-less where `getAll` correctly caps at 200. Correct
today, but grows without bound per user. Phase 17 (performance) material.
