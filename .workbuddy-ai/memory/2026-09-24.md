## Phase 8 — Notifications. One defect found and fixed.

### FIXED: `POST /alerts` answered 500 for a bad request

`alertController.create` passed the body straight to `notificationService.notify()`,
which raises a **plain `Error`** for a missing title/message/addressee. A plain
Error is not an `ApiError` and has no `ER_` code, so `errorHandler` fell through
to its default: **500**, with the message masked to "Internal server error" in
production. The caller got a server fault with nothing to act on.

Measured against the deployed API before the fix:

    POST /alerts {}                    -> 500
    POST /alerts {title, message}      -> 500   (no addressee)
    POST /alerts {targetRole}          -> 500   (no title/message)

Fixed by validating in the controller (400s) before calling the service, plus a
new guard: an unrecognised `targetRole` is rejected instead of being stored
verbatim. An unknown role produces a row addressed to a role nobody holds —
readable by nobody — which is the same unreadable shape as the 14 legacy
addressee-less rows the service already documents as a bug.

Safe to change: the frontend has **no create-alert UI at all** and never sends
`targetRole` (only reads it), so `POST /alerts` is API-only. Nothing on screen
could break.

**Technique worth reusing — a behavioural controller test with no database.**
Validation runs *before* any I/O, so the controller can be driven directly with
fake `req`/`res` and a `next` that captures the error, and the assertion can be
on the real status code rather than on source text. This is stronger than the
repo's usual file-scanning style and is how the 500 was pinned. `config/database`
builds a pool at import but `createPool` does not connect, so requiring the
controller is safe.

**And the fix was verified by breaking it.** The validation was neutered in place
(three `if`s → `if (false)`, the two `throw` lines deleted), the suite re-run to
confirm the new test *failed* (39 pass / 1 fail — exactly the new test), then the
fix restored. A guard that cannot fail is decoration; this one was proven.
Restoring needed care: **`git checkout` would have been wrong** because the fix
was uncommitted, so HEAD did not contain it.

### FOUND, NOT FIXED: `DELETE /alerts/:id` destroys a shared alert for everyone

`/alerts` is mounted with `authenticate` only — no module guard. `remove()`
deletes the row itself (`DELETE FROM alerts WHERE id = ?`) plus its `alertReads`,
and the only check is `findVisible`, i.e. "can I see it". So **any authenticated
user who can see a role-addressed alert can delete it for every other
recipient** — 11 Houseparents share one alert and any one of them removes it from
all 11 feeds.

This contradicts the module's own central design principle. Read state was moved
to a per-user `alertReads` table precisely so one recipient's action could not
affect another's view; deletion is the one operation still global.

Reachable from the UI: `DataContext.tsx:1025` calls `deleteResource('alerts', id)`
and `Notifications.tsx` exposes `deleteAlert` to every role.

Probed non-destructively (non-existent id, so nothing could be deleted):

    DELETE /alerts/ALR_NONEXISTENT_PROBE  as nurse       -> 404  (reachable; no guard)
    DELETE /alerts/ALR_NONEXISTENT_PROBE  as centerhead  -> 404
    PUT    /alerts/ALR_NONEXISTENT_PROBE  as nurse       -> 404  (reachable)

A 404 rather than a 403 is the tell: the route is reachable and the only thing
that stopped it was visibility.

Needs a decision, not a patch. Options: (a) add an `alertDismissals` table and
make dismissal per-user, consistent with `alertReads` — correct, but a schema
change; (b) restrict DELETE to `targetUserId === me` or a manager role — small,
but it 404s the existing per-user "dismiss" button for role-addressed alerts.
Both change UX, so this is the user's call.

## The pattern that fixed items 50 and 51 (reuse this)

Both were the same defect: **a relationship keyed on a display name.** The fix
shape, applied twice, works well:

1. Add an id column *beside* the name (`admissions.houseparentUserId`,
   `accessRequests.reviewedById`). The name stays, because it is what gets
   printed — it becomes a label again instead of the link.
2. Read the id first. Gate the old name comparison on `<idColumn> IS NULL`, so it
   is a migration aid for pre-existing rows and can never override a recorded id.
3. Backfill, but only where the name resolves to **exactly one** account. An
   ambiguous name is left NULL, which means the row keeps its old behaviour — the
   backfill can make a link more precise, never reassign one person's data.
4. An id that names nobody is a **400**, not a stored dangling reference.
5. Declare the column in *every* place the table is created (here: the
   controller's `ensureTable`, `server.js`'s boot migration, and `schema.sql`).

The failure mode this class produces is always silent — the wrong list is simply
returned — so it needs tests, not a smoke test.

## Windows pitfalls that cost real time today (both are traps)

**1. Python text-mode rewrite converts LF → CRLF.** `io.open(p, 'w')` on Windows
writes `\r\n`. Any test that locates a block with a multi-line marker containing
`\n` then silently stops matching: `indexOf` returns `-1` and `slice(-1)` yields a
one-character block, which makes assertions fail — or, with a loose pattern, pass
for the wrong reason. Two defences, both now in place:
- Normalize on read: `read = (rel) => fs.readFileSync(...).replace(/\r\n/g, '\n')`.
- Assert the markers were found and the block is plausibly long before asserting
  anything about its contents. (`houseparent-assignment-identity.test.js` has a
  `between()` helper plus a "the reader blocks were located" test.)

Use `io.open(p, 'w', newline='')` to write LF deliberately.

**2. Python resolves `/tmp` as `C:\tmp`.** A helper written by a bash heredoc to
`/tmp/x.py` is not visible to `python /tmp/x.py` (Git Bash's `/tmp` is elsewhere).
Use `python "$(cygpath -w /tmp)/x.py"`.

## Test techniques added this pass

- **Extract a TypeScript function and run it.** For a pure frontend predicate
  there is no runner, and a shape assertion cannot see a behaviour. Strip the
  signature annotations (`export`, `?: T | null`, `): boolean`), then
  `new Function('dep', body + '; return fn;')(stub)`. This is how
  `isTodayOrLater` is tested against a stubbed clock.
- **Strip comments before asserting on code.** A fix whose comment quotes the
  expression it removed trips a naive "the old code is gone" regex — this bit twice
  in one file. `code(src)` removes `/* */` and `//` first.
- **Make the pool stub apply the write.** A stub that returns a fixed row makes
  the handler's read-back report the pre-update state and the assertion fails for
  the wrong reason. Parse the params and mutate the stub row.
- **Stub sibling modules by resolved path.** `require.resolve('./assignmentController')`
  in a test resolves relative to the *test*, so it throws MODULE_NOT_FOUND; use
  `'../src/controllers/assignmentController'`.
- **`includes('Section Name')` survives the section being deleted**, because the
  same words sit in a nearby comment. Match the rendered heading
  (`/>Assigned Schedules<\/p>/`). Two mutations escaped the item-46 guard this way
  before the assertions were tightened.

# Item 28 — the QPR closing narrative (`70b3ea8`)

One free-text `narrative` on `quarterlyProgressReports`, printed between the last
aspect row and the signature. `drawNarrativeSection` + `wrapNarrative` in
`quarterlyReportPdf.js`; the geometry entry `narrative` in
`quarterlyReportTemplate.json` is what the editor positions its textarea from.

**The signature band now hangs off the narrative, not off the last row.**
`TEMPLATE_GEOMETRY` computes `signatureStart = narrativeBottom - NARRATIVE_TAIL`.
Deriving it from `tableTops[1] - rows * rowHeight` as before would print the
signature over the box. If you move the box, the band follows; if you change the
band back to the row, `signature.top` in the shared JSON must change with it or
the agreement test fails.

**`wrapToWidth` drops a blank paragraph** (`if (words.length === 0) continue`),
which is right for a bullet list in a cell and wrong for prose — two paragraphs
would run together. `wrapNarrative` wraps each paragraph separately and pushes
`''` for a blank one; `drawNarrativeSection` advances the cursor for `''` without
calling `drawText` (pdf-lib has no use for an empty string).

**A finished report with an empty narrative prints no section at all.** Only the
template always draws the box. That keeps an existing report's PDF unchanged and
stops a finalized document showing an empty ruled box.

## The push blocker: a GUI credential selector, not the network

Long-standing symptom: `git push`, `git fetch` and `git ls-remote` all hung until
SIGTERM, in and out of the sandbox, with `GIT_HTTP_LOW_SPEED_*` tuned. It was
never the network and never auth.

The differential test that isolates it:

| command | result |
|---|---|
| `curl …/SCH-PATH.git/info/refs?service=git-upload-pack` | HTTP 401 in 0.4 s |
| `git -c credential.helper= ls-remote origin` | instant `fatal: could not read Username` |
| `git ls-remote origin` (default config) | **hangs** |
| `git -c credential.helper= -c credential.helper='!"…/git-credential-manager.exe"' ls-remote origin` | instant |

Cause: PortableGit's **system** gitconfig (`PortableGit/<ver>/etc/gitconfig`) sets
`credential.helper = helper-selector`, which resolves to
`git-credential-helper-selector.exe`. The DLLs beside it (`Avalonia.dll`,

## The sandbox drops writes to refs/remotes

`git fetch` prints `master -> origin/master` but the local ref never moves,
because `.git/refs/remotes/origin/` cannot be created — the tool sandbox discards
it. `refs/heads/` *is* writable (that is why commits persist), and
`git update-ref refs/remotes/origin/master` silently fails too. `origin/master`
lives in `.git/packed-refs`, so correcting that one line by hand is what makes
`git status` honest. A stale `origin/master` is what made the backlog read
"35 ahead" when the remote was in fact 4 commits behind.

**Read the remote, not the local ref, before reporting unpushed work:**
`git ls-remote origin master`.

## Seed `assignmentType` typo fixed (policy answer: "typo")

`seedResidentAssignments` wrote `assignmentType = 'household'`; every scope
reader requires `'houseparent'`. Confirmed a **typo**, not a deliberate
whole-facility placeholder: `'household'` had **no counterpart writer anywhere**
(the assignment UI posts `'houseparent'`; `assignmentController` passes through
whatever it is handed), and the function's own log line already said
"houseparent -> child". So every seeded row was inert, and a seeded Houseparent
signed in to an empty caseload.

Effect worth remembering: the loop is the **full houseparent × child cross
product**, so now that the value is live, every seeded Houseparent is assigned
every Active resident. Seeded data therefore cannot demonstrate per-Houseparent
isolation. Real UI assignments are one-resident-at-a-time and unaffected.

Decided in the same round: `/violations` and `/phaseProgress` stay
**facility-wide** for Houseparents — intended, not an oversight. So
`tests/caseload-scope.test.js` lost the test asserting those two controllers
consult the caseload scope: its premise was rejected, and a permanently skipped
test is just a stale known-issue. The other skipped test was un-skipped and
mutation-verified — flipping the seed literal back to `'household'` fails it
with the exact diagnostic.

Suite **1073 / 1073 pass / 0 fail / 0 skipped** (was 1074/1072/0/2: one test
deleted, one un-skipped). Commit `effd62d`, pushed on attempt 1.

### The fix is forward-only — read this before assuming live changed

`seedDatabase()` runs **unconditionally at boot** (`server.js:2515`, before
`app.listen`), so the corrected literal does ship. But it changes nothing on a
database that has already been seeded, because the idempotency key ignores the
assignment type:

```js
const [existing] = await pool.query(
  "SELECT userId, residentId FROM residentAssignments WHERE status = 'Active'");
const existingKeys = new Set(existing.map(r => `${r.userId}|${r.residentId}`));
```

Every `(userId, residentId)` pair already exists — inserted with the old
`'household'` value — so no `'houseparent'` row is ever created for those pairs.
The fix therefore only takes effect on a **freshly seeded** database. Making the
live demo behave as intended needs a one-time rewrite of the existing
seed-generated rows, which changes who can read whose records, so it was left for
an explicit decision rather than done silently.

Also checked: the seed never writes `admissions.houseparentOnDuty` /
`houseparentUserId`, so the legacy compatibility path in `residentScope.js`
cannot rescue seeded Houseparents either. That is consistent with the measured
"HP sees 0 children" on live. `assignmentType` is plain `VARCHAR(50)` (no ENUM)
in all three schema definitions, so the new value cannot fail a constraint.

**Decision (2026-09-24): leave the existing rows inert.** No backfill, no boot
migration, no opt-in script. Reason: `seedResidentAssignments` creates the full
cross product and the seed inserts **only users** — no children, no admissions —
so on the live database those rows already span the *real* residents. Converting
them would have given every Houseparent access to every child's records.

**Residual risk to keep in view:** now that the seed writes a live value, a
*fresh* database (empty `residentAssignments`) seeded at boot will assign every
active Houseparent to every active child. Harmless on the current DB because all
pairs already exist, but it is a real access change if the assignment table is
ever emptied or the app is pointed at a new database.
