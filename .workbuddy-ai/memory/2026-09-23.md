  (`documents.fileData`, `education_records.fileData`, plus ~14 signature columns).

- `vite.config.ts` dev proxy targets `http://localhost:5000`; `api.ts` already does

# Session 3 — Returning-resident documents merge (3rd+ admission)

**Reported:** admission 2 separates correctly; from admission 3 onward, previous
admissions' documents merge together.

## Root cause

`healthController.publishDocumentForHealthRecord` is called from both create and
update via `publishSafely`. Its re-publish branch **unconditionally** re-resolved
`documents.admissionId` from the resident's *current* admission
(`activeAdmissionIdFor(pool, record.residentId)`) and overwrote the existing
row's link. So any later edit to an older health record silently dragged that
document into the newest admission folder, permanently.

TRI / Anecdotal / QPR publishers do **not** do this (their UPDATE never touches
`admissionId`; only the INSERT derives it). Verified by elimination.

**Fix:** read the stored `residentId`/`admissionId`, compare against the incoming
record; re-resolve **only** when the record genuinely moved to another resident,
otherwise carry `previous.admissionId` through untouched.

## Second root cause — the column had no runtime migration

`documents.admissionId` is in `schema.sql` (so fresh installs are fine) but
`CREATE TABLE IF NOT EXISTS` does nothing to an existing table, and there was
**no `ensureColumn` for it**. `migrate_document_admissions.sql` exists as a file
but nothing in `server.js` runs it — it was a manual phpMyAdmin step.

So on any **upgraded** deployment the column was absent and every document fell
back to timestamp inference → all admissions merged. Worst kind of bug: invisible
on a fresh install, guaranteed on a real one.

**Fix:** `ensureColumn('documents','admissionId',…)` + index + a new
`backfillDocumentAdmissions()` at boot, mirroring both passes of the SQL file
(latest admission in force when the document was written; earliest admission as
fallback). Idempotent — only rows with `admissionId IS NULL`.

## Third root cause — phase archival was resident-scoped

`admissionController` and `childController.readmit` both archived phases with
`WHERE residentId = ?`, and `phaseProgress` had **no `admissionId` column** at
all. `isCurrent` is per-resident, so a re-admission closed *every* phase the
resident had ever had — including the newest admission's.

**Fix:** new `phaseProgress.admissionId` column + `backfillPhaseProgressAdmissions()`
(placement = highest admission whose `admissionDate <= enteredAt`), both archival
statements scoped to the admission being closed (`admissionId = ? OR admissionId
IS NULL`, the NULL arm for pre-migration rows), and the new phase row anchored to
the admission it belongs to.

## Fourth — the legacy `readmit` path

`POST /api/children/:id/readmit` (`childController.readmit`, wired into
`DataContext.readmitChild`) wrote `previousCases` entries as
`{offense, date, dischargeDate}` — **no `admissionId`, no `admissionNumber`** —
and created **no `admissions` row**. That is precisely the shape that trips the
resolver's untrusted-link guard and merges everything. Unreachable from the UI
(no component calls `readmitChild`) but live on the API.

**Fix:** rewritten to write the same shape the admissions controller does —
proper `previousCases` entry with `admissionId`/`admissionNumber`, an `admissions`
INSERT, an admission-linked phase INSERT, and the scoped archival.

## Fifth — `PhaseProgress` was a third, independent admission filter

It compared only `uploadedAt` against the readmission cutoff. A document filed
under an earlier admission but uploaded today therefore showed as current.

**Fix:** it now builds the same period list via `admissionPeriodsFor` and honours
`document.admissionId` first, falling back to the timestamp only for unlinked rows.

# Session 4 — Documents module modal overlay (Esc-only) bug

## Root cause: Radix `DismissableLayer`, not z-index

`@radix-ui/react-dismissable-layer` computes whether a layer may receive pointer
events from its position in an **insertion-ordered `Set`**:

```js
const highest = [...layersWithOutsidePointerEventsDisabled].slice(-1)[0];
const isPointerEventsEnabled = layers.indexOf(node) >= layers.indexOf(highest);
style: { pointerEvents: isBodyPointerEventsDisabled
  ? (isPointerEventsEnabled ? 'auto' : 'none') : undefined, ...props.style }
```

A workflow that shows a confirm then an outcome opens two layers moments apart.
If the outgoing layer is still in the `Set` when the incoming one measures
itself, the incoming dialog is judged "not the top layer" and Radix **inlines
`pointer-events: none`** on it. It still paints, and **Esc still works** (Escape
is a document-level key handler, not a pointer event) — exactly the report.

`...props.style` is spread *after* the computed value, so an app-supplied
`style` wins. That is the lever.

## Two-layer defence

1. **`ui/modalLayer.ts`** exports `modalPointerGuard = { pointerEvents: 'auto' }`.
   Applied in **both** `ui/dialog.tsx` and `ui/alert-dialog.tsx` as
   `style={{ ...modalPointerGuard, ...style }}`. `SystemDialog.tsx` previously
   inlined a copy of this with a comment about the same bug — now it imports the
   shared one. Deliberately *not* a z-index change: raising z-index fixes the
   look while leaving the dialog inert.
2. **`SystemDialog.tsx` provider yields a frame** before replacing a dialog, so
   the outgoing Radix layer leaves the `Set` first. Needs `layerMounted` (is a
   layer on screen?) tracked separately from `resolver` (is a caller still
   awaiting?) — `resolver` is `null` the instant a button is pressed, which is
   precisely the risky handoff. Plus `cancelQueued` so the latest replacement
   wins the frame race.

## Third rule: callers close their own dialog before the first await

Two real defects found by this rule, both in the reported path:
- `DocumentUpload.handleReject` — closed after `await request` **and**
  `await refreshData`; the `catch` never closed it at all.
- `Tri.handleSubmit` — closed after `await dialog.confirm(...)`, i.e. the form's
  layer was mounted *while* the confirm was on screen. Fixed by hoisting the
  close above the confirm; the duplicate in the `catch` removed.
Already-correct: `DocumentUpload.handleReviewSubmit`, `Tri.handleReturn`,
`Tri.handleFinalize`, `AnecdotalReports.confirmSubmit`.

## Tests: `backend/tests/modal-stacking.test.js` (11) + `tests/helpers/scan-modal-order.js`

### Traps hit while writing the guards (worth remembering)
- `[\s\S]*?\n  \}` truncates a handler at the first nested closing brace. Use
  **brace balancing**, not a non-greedy regex.
- Comment prose containing the word **`await`** ("closing afterwards would leave
  this layer mounted") makes a first-await search report a false positive. Strip
  comments before measuring.
- The close-call regex `set[A-Z]\w*(?:Dialog|Modal|Form|Overlay)\w*Open\(false\)`
  **matched almost nothing** — `\w*` runs greedily past the keyword, and
  `setShowForm(false)` has no `Open` at all. The working pattern is
  `\bset\w*(?:Dialog|Modal|Form|Overlay)\w*\(false\)`. A detector that can never
  fire is worse than no detector; there is now a test asserting the detector
  matches all seven real call shapes.
- Splitting source at handler headers misattributes nested functions. Balance
  braces from the handler's own `{`.

# Session 7 — cross-device verification (phone → PC), found 2 more real bugs

User asked: after deploy, open on Android + PC; upload on phone must appear on PC.

## Answer to the question: yes, cross-device sync works by design

- Documents are stored in MySQL: `documents.fileData` is a `LONGTEXT` column.
  Not device-local, not on a local disk.
- `refreshData()` → `getStore()` → `request('/store')` → live server call.
  Called on mount AND on window focus (`DocumentUpload.tsx:641-642`).
- `fileData` is deliberately excluded from the `/store` bulk payload (size), so
  bytes are fetched per-document from `GET /api/documents/:id/file`.
- **No document data in `localStorage`** — the only thing stored there is the
  auth token. All 4 DocumentUpload localStorage uses are token reads.
- CORS matches on **origin, not device** — phone and PC both send the Vercel
  origin, so one `CORS_ORIGIN` value covers both.

## BUG FOUND AND FIXED #1: 8 (actually 9) raw fetch calls bypassed VITE_API_URL

`request()` builds `${API_BASE_URL}${path}`, but the binary/PDF endpoints use raw
`fetch()` (they need a Blob) and were written with a literal `'/api/...'`, which
resolves against the **page** origin.

On Vercel the page origin is the Vercel host, and the SPA rewrite turns `/api/...`
into `index.html` → `res.ok` is **true** and the "file" is the app's HTML.
Verified with the real rewrite regex: `/api/documents/x/file` → REWRITE.

Would have broken, on both devices: document View / Download / Print, bulk ZIP,
Anecdotal Report PDF, Quarterly Progress Report PDF + its `/template`.

Note: `api.ts`'s own `API_BASE_URL` comment describes this identical bug for the
non-binary calls — it was fixed there but the raw fetches were missed.

Fixed: exported `API_BASE_URL`, added `apiUrl(path)` + `authHeaders()`, and
rewrote all 9 sites. `tests/api-base-url.test.js` (4 tests) guards it, verified
to fail when reverted. My first grep missed the 9th (multi-line) so the test now
scans every line of every `.ts/.tsx`.

Static assets (`/forms/*.pdf`) correctly stay same-origin — a test asserts
`apiUrl()` is never used for them.

## BUG FOUND AND FIXED #2: uploads 7.5–10 MB refused (worst on mobile)

A file is sent base64 inside a JSON body → ~4/3 inflation. Three numbers must
agree and live in two files:
- the label "Max 10MB"
- the client check `file.size > 10*1024*1024`
- the server `express.json({ limit: '10mb' })` ← applies to the BODY

So a 10 MB file = 13.3 MB JSON → **413 from body-parser before any handler runs**
→ surfaced as bare "Request failed". Real ceiling was ~7.5 MB.

Worst on a phone: camera photos/scans are routinely 8–12 MB, so the uploads most
likely to be attempted from Android were the ones refused.

Fixed: server limit → `16mb`; client ceiling is now `MAX_UPLOAD_BYTES` /
`MAX_UPLOAD_LABEL` used by both the check and the label.
`tests/upload-limits.test.js` (5 tests) verifies body ≥ base64(file) + headroom
and specifically that an 8 MB photo fits. Verified to fail at `10mb`.

## Session 8 — multi-user correctness (845 tests, all green)

Brief: *"I want all the users using the website at the same time no flaws, can
interact to the system based on their rbac."* Five real defects found, all of
which only appear with more than one concurrent user.

1. **Client-minted record ids collided.** `DataContext.generateId()` computed the
   next sequential id from the visible list (`CH001`→`CH006`) and posted it as the
   record's id. The backend ignores a client id and allocates its own
   (`insertWithGeneratedId`), so no request *failed* — but the optimistic row was
   reconciled by `prev.map(d => d.id === tempId ? saved : d)`, which could never
   match. Two concurrent creates → unresolvable phantom row.
   `Health.tsx` had a second instance (`genHealthId`, `HLT<n>`).
   Fix: removed every client id mint; server allocates. `provisionalKey()` is the
   only client key and is never sent.

2. **Out-of-order `/store` refreshes.** Fired on mount, window focus and after
   actions, with no in-flight tracking — a slow earlier response could overwrite
   newer state. Fix: `loadGeneration` / `alertLoadGeneration` refs; only the
   newest response writes (including the error path and `isLoading`).

3. **Lost updates.** Two editors = silent last-write-wins, and partial payloads
   (`{ notes }`, `{ phaseTasksCompleted }`) clobbered fields they never mentioned.
   Fix: opt-in optimistic concurrency. Client sends the `updatedAt` it rendered
   (`withVersion()`); `baseController.update` returns **409** when the stored row
   is newer. Omitting `updatedAt` behaves exactly as before.

4. **SECURITY — caches survived logout on a shared workstation.**
   `AuthContext.CACHED_DATA_KEYS` had drifted from what components write:
   it cleared `educationSchoolVisits` / `educationMonthlyReports` but
   `Education.tsx` writes `educationVisitReports` / `educationProgressReports`;
   `educationStudents` and `userAccounts` were never cleared at all. The next
   person on that machine could read the previous user's Education records and
   the account roster straight out of `localStorage` — no API call, no role
   check. Fix: corrected list + `tests/session-cache.test.js`, which reads the
   key literals out of the writers.

5. **Connection pool was hard-coded at 10.** Now `DB_POOL_LIMIT` (default 20,
   capped 200) so it can sit under the provider's connection cap. Too high gives
   "Too many connections" for everyone at once.

Verified clean and *not* changed: no cross-request RBAC caching (snapshot rebuilt
per request from a fresh DB read), rate limiter keyed per-IP-per-username,
password hashes stripped server-side, every `getConnection()` has a matching
`release()` (and `release()` is in a `finally` in the retry loop), JWT secret
placeholder guard enforced at boot.

New tests: `concurrent-users.test.js` (23), `session-cache.test.js` (9).
All five fixes verified by reverting each and confirming the new tests fail.

## Account Management user creation — online fix (11:50)

**Defect (6th of the same class).** `AccountManagement.handleAddUser` built the
new account with `id: \`U${String(Date.now()).slice(-4)}\`` and posted that
object as the body — so the id *was* transmitted. Truncated to four digits,
`Date.now()` repeats every 10s, so two admins submitting in the same
millisecond derived one id. The backend was already correct
(`userController.register` allocates via `insertWithGeneratedId` and ignores any
body id), so nothing *errored*: the account was created under the server's id and
appended locally under the client's, leaving a row that vanished on reload.

**Fix.** Dropped `id` from the payload; the local list is now rebuilt from the
API response (`[...users, saved]`) instead of an optimistic guess.
