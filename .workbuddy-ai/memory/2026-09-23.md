## Fixed (all 12 failures now green — 766/766 pass)

1. **SECURITY — document upload guard bypassed (real hole).**
   `backend/src/utils/constants.js` `DOCUMENT_ROLE_PERMISSIONS` was missing three
   title-case aliases the frontend sends and requires: `'Court Order'`,
   `'OCP Resolution'`, `'Diversion Plan Referral Letter'`.
   `documentController.create()` does `if (allowedRoles && ...)` — so a **missing
   key skips the role guard entirely**. Any role (e.g. Nurse) could POST these.
   Added the three aliases. (`'Medical Certificate / Birth Certificate'` and
   `'Baptismal Certificate'` were already present, so Admission was only partly open.)

2. **SECURITY — `requiredTasks` leaking into the upload picker.**
   `DocumentUpload.tsx` `allowedDocuments` loop folded `requiredTasks` into the
   document list. Task names ("Counseling sessions") became offerable documents
   with no permission entry → again an open upload. Now reads only
   `requiredDocuments` + `optionalDocuments`.

3. **Test was wrong, not the code — `document-access-request.test.js`.**
   The "every document type offered by a phase has a permission entry" test
   scraped *every* quoted string in the PHASE_REQUIREMENTS block, including
   `requiredTasks`. Its own comment said it checks document types. Narrowed to
   the two document list fields. (First attempt using `indexOf(']')` was buggy —
   it stopped at the array of the first field; final version uses a regex over
   `(requiredDocuments|optionalDocuments):\s*\[([^\]]*)\]`.)

4. **RBAC — Houseparent held `Child Records` + a Medical tab**, contradicting its
   own description ("No medical, health, court or administrative access") and the
   spec in `rbac.test.js`. Removed the module and its `subModules`/`permissions`
   entries from `rbac.definition.json`. **Then copied the file to
   `frontend/src/app/config/rbac.definition.json`** — a test asserts the two are
   byte-identical.

5. **SECURITY — redaction failed OPEN (the subtle one).**
   `childController.mayReadResidentMedicalSummary` / `mayReadHealthRecords`
   called `buildAccessSnapshot`, which treats an **empty `accessibleModules` as
   "fall back to the role's full matrix"** (`rbac.js` line ~313). A Houseparent
   row with `[]` stored — which is exactly how the role is seeded — therefore
   resolved to its whole matrix and was handed `medicalRecords`.
   Added `roleCanReachMedicalTab(role)` / `roleCanReachHealth(role)` which read
   the **role definition, never the stored grant**, and fail closed. An unknown
   role is refused.

6. **Same trap removed in `accessDefaults.js`.** `DEFAULT_CHILD_RECORD_TABS` had
   a `houseparent: [...CHILD_RECORD_TAB_ORDER]` entry for a module the role does
   not hold. Deleted it and made `defaultsForRole()` return
   `childRecordTabs: []` unless the role's modules actually include Child Records.
   NOTE: needed `rbac.CHILD_RECORD_TABS_MODULE` (the bare name is not in scope in
   that file) — the first attempt threw at runtime and broke 12 unrelated tests.

7. **Discharge Report lost one of its two signatures.** `PhaseProgress.tsx` had
   been reduced to a single Center Head pad. Restored:
   `buildDischargeReport(preparedBySignature, approvedBySignature)`, two
   `SignaturePadModal` pads labelled `"Prepared by signature"` and
   `"Approving authority signature"`, two `.signature-slot` marks (CSS moved from
   a centered single column to a two-column `.signature-block` flex, slot height
   40px → 60px), and two embedded `<img>`. The test pins the literal parameter
   names AND `buildDischargeReport(dischargePreparedBySignature, dischargeApprovedBySignature)`,
   so the local state names are load-bearing: `dischargeSignerName`,
   `dischargePreparedBySignature`, `dischargeApprovedByName`,
   `dischargeApprovedBySignature`.

8. **Test asserted a calling convention, not a behaviour —
   `admission-period-folders.test.js`.** The literal
   `renderCategoryFolder(periodKey, folder, folderDocs)` no longer matched because
   the renderer gained a trailing `admissionOrdinal` argument. The code was
   correct. Relaxed to `renderCategoryFolder(\s*periodKey,\s*folder,\s*folderDocs\b`.

## Deployment constraints discovered (IMPORTANT)

- **All uploaded files are base64 inside MySQL `LONGTEXT` columns**
  (`documents.fileData`, `education_records.fileData`, plus ~14 signature columns).
  There is **no filesystem/S3 storage layer**. Two consequences:
  1. Free Postgres (Supabase/Neon) is a poor fit — the code is MySQL-specific
     (`mysql2/promise`, `ER_DUP_FIELDNAME`, `INFORMATION_SCHEMA.COLUMNS`,
     `ENGINE=InnoDB`, `ON DUPLICATE KEY UPDATE`, `max_allowed_packet`).
     Use **MySQL** (Railway / Aiven / Clever Cloud free tiers).
  2. Free tiers often cap DB size well below what a base64 document archive needs.
     This is the #1 sizing risk.
- **The backend reads PDFs/logo out of the frontend tree**, resolved relative to
  CWD/`__dirname`: `frontend/public/forms/*.pdf` (Anecdotal Report, tri.pdf,
  incident-report.pdf) and `frontend/src/assets/sch-logo.png` for health/quarterly
  PDFs. A backend-only deploy **must** carry those files.
- `server.js` can serve `frontend/dist` itself (SPA fallback). If deploying frontend
  to Vercel separately, that path is simply unused.
- `vite.config.ts` dev proxy targets `http://localhost:5000`; `api.ts` already does
  `import.meta.env.DEV ? VITE_API_URL : '/api'` — so a production build always calls
  same-origin `/api` unless changed. **This needs a production API base URL.**
- `server.js` has `app.use(cors())` with no origin restriction — for a split
  Vercel + separate-backend deploy this must become an allow-list.
- Seed data / default users live in `src/scripts/seedDatabase.js`; JWT_SECRET is
  validated at boot (`utils/security.js`) and the process refuses to start on a
  placeholder secret, min 16 chars.
